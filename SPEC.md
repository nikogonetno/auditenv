# SPEC.md. RL-среда для ИИ-аудитора

Статус: **черновик v2 от 19.11.2026, ждёт подтверждения A и B.** После подтверждения меняется только через PR, который видят оба.

Единственный источник правды для кода. Собран из решений версии 2 в плане команды, доменной спецификации A, QA-отчёта v0.1 и комментариев PM от 19 ноября. При расхождении верно следующее: схема файлов, контракт и оценка берутся из этого документа, типы ошибок, варианты, сценарии и двойники берутся из спецификации A.

Метки в тексте:

- **[v2]** решение версии 2, принято, замораживаем
- **[предложение]** рекомендация QA или архитектора, нужно «да» от PM или обоих
- **[кейс §NN]** сверить дословно с текстом кейса. Текста кейса в репозитории нет, поэтому здесь ничего не выдумано

## 1. Рамка

- Python 3.11, только стандартная библиотека. Runtime-зависимостей ноль, это проверяет тест `test_no_runtime_dependencies`.
- Без сети, GPU, базы данных, веб-сервера и внешних API.
- Одна команда проверки `make verify`, она запускает `scripts/verify.sh`. Тот же скрипт стоит в CMD Docker-образа.
- Тесты пишутся на `unittest` и запускаются через `python -m unittest`. pytest умеет их запускать, но не обязателен.

## 2. Детерминизм [v2]

- Случайность только через `random.Random(seed)`. Модульный `random`, `secrets`, `uuid` запрещены.
- Деньги только в целых минимальных единицах, курсы только через `Decimal`, округление `ROUND_HALF_UP`. `float` в суммах и курсах запрещён.
- Любой вывод, построенный обходом `set` или `dict`, идёт через `sorted`. JSON пишется с `sort_keys=True`, `ensure_ascii=False`, `indent=2`. CSV пишется с `lineterminator="\n"`.
- Запрещены `datetime.now()`, `time.time()` в данных, `hash()` и `id()`.
- Время хранится с фиксированным сдвигом, явный сдвиг стоит в каждом timestamp. tzdata и `zoneinfo` не используем.
- Проверка: два процесса с разным `PYTHONHASHSEED` дают одинаковые sha256 всех файлов, наблюдений, наград и траекторий (INV-24, E-15).
- **Подвох.** `python -I` подразумевает `-E` и молча игнорирует `PYTHONHASHSEED`. В тестах детерминизма дочерний процесс запускаем с `-P -s` и чистим унаследованные `PYTHON*`, как в `tests/test_golden_fixture.py`.

## 3. Файлы эпизода

### 3.1 Раскладка

Эпизод состоит из двух папок. `public/` агент видит только через инструменты среды. `private/` читает только оценщик, и только при submit. Все суммы хранятся целыми числами в минимальных единицах, все времена в ISO 8601 с явным сдвигом.

### 3.2 Открытые файлы [кейс §03, решения PM 20.11; эталон формата `tests/fixtures/mini_v03`]

Обязательные поля и ключи кейса §03 идут первыми и в его порядке, доменные поля A после них. Других открытых файлов нет: `counterparties.csv`, `allocations.csv` и `accounts.csv` убраны (правило PM по умолчанию). Имя контрагента лежит в документах, план счетов в `policy.json`, разнесения видны в `ledger.csv` по паре `payment_id` и `invoice_id`.

| Файл | Обязательное по кейсу §03, в этом порядке | Доменные поля после |
|---|---|---|
| `manifest.json` | `schema_version, episode_id, base_currency, period_start, period_end, timezone`, число записей по таблицам `counts`, число документов `documents`, правила округления `rounding` | нет |
| `invoices.jsonl` | `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items` (`line_id, description, qty, unit_price_minor, amount_minor`) | `direction, counterparty_name, invoice_number, vendor_ref, po_ref, entered_at, service_from, service_to` |
| `payments.jsonl` | `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs` | `entity_id, direction, counterparty_name_raw, entered_at, remittance_info` |
| `ledger.csv` | `row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id` | `je_id, entered_at, doc_currency, doc_amount_minor, exchange_rate, memo` |
| `fx.csv` | `date, source_currency, target_currency, rate` | `fx_id` |
| `policy.json` | выбор даты курса, границы периода, округление | см. §3.5 |

Значения полей:

- `timezone` это фиксированный сдвиг компании вида `"+05:00"`.
- `timestamp` в `ledger.csv` это полное время ISO 8601 со сдвигом компании. Период строки определяется местной датой `timestamp`.
- `timestamp` платежа это время из банковской выписки, ISO 8601 с явным сдвигом (`+00:00`, а не `Z`).
- `entity_id` это ID контрагента. У неопознанного поступления он `null`.
- `invoice_refs` это отсортированный список `invoice_id`, на которые указывает назначение платежа. Если ссылки нет, `null`. Если ссылка подходит к нескольким счетам, как в C2, в списке все они.
- Отсутствующие ссылки это явный `null`: пустая ячейка CSV или `null` в JSON (кейс §03).
- `debit_minor` и `credit_minor` в базовой валюте, заполнена ровно одна из двух, `currency` равна базе.
- У строк счёта заполнен `invoice_id`. У строк платежа заполнен `payment_id`, у строк погашения 1210 и 3310 ещё и `invoice_id` погашаемого счёта.
- В валютных платёжных проводках есть строки курсовой разницы 6250 и 7430.
- Колонка курса называется `exchange_rate`, а не `fx_rate`, иначе имя типа ошибки попадёт в открытый файл (INV-23).
- JSONL пишется одной строкой на объект с ключами в порядке таблицы. JSON пишется с `sort_keys=True, indent=2`. CSV пишется с `lineterminator="\n"`.

### 3.3 Идентификаторы [v2]

- ID состоит из 6 символов Crockford Base32 и берётся из `random.Random(seed)`. ID назначаются после инъекций и уникальны между всеми таблицами. Уникальность проверяет `test_ids_are_unique_across_tables`.
- Ссылаться на запись можно как `<таблица>/<id>` или как голый `<id>`, matcher принимает обе формы. Снимается только известный префикс: `invoice`, `payment`, `ledger`, `allocation`, `counterparty`, `line`, `fx`, `doc`. Это тот же список из восьми, что в §5.2 (QA D-3). Для документа годятся и `doc_id`, и `invoice_id` или `payment_id`.
- У строки `fx.csv` обычный ID `fx_id` без слешей, ссылка на неё `fx/<fx_id>` (QA P-04, принято PM).
- `invoice_number` и `vendor_ref` это деловые атрибуты, а не ID. Смена ID их не трогает, truth на них не ссылается.
- `je_id` остаётся дополнительной колонкой для группировки строк проводки. В `affected_ids` он не попадает.

### 3.4 Время и период [v2]

- У компании фиксированный сдвиг из `+03:00, +04:00, +05:00, +06:00`. Он записан в `manifest.json` и `policy.json`.
- Период равен календарному месяцу по времени компании. Окно книги шире периода на 7 дней с каждой стороны, и с каждой стороны в нём не меньше 10 настоящих строк соседних периодов (INV-03).
- Дата проводки равна местной дате `issued_at` счёта или `timestamp` платежа. `entered_at` на дату не влияет.

### 3.5 policy.json

- Структура одинаковая во всех эпизодах, у чистых и у ошибочных (R-06, E-19). Правило не появляется только там, где есть ошибка.
- Правила учёта берутся из раздела «Правила учёта» спецификации A.
- В `policy.fx` нерабочие дни заданы двумя полями: `weekend_days` с номерами дней ISO и `holidays` со списком дат (QA P-05, принято PM). ISO это понедельник 1 … воскресенье 7, то есть `date.isoweekday()`, а не `weekday()`, где понедельник 0. Иначе курс субботы попадёт не на тот день, и стресс упадёт на INV-18.
- План счетов лежит в `policy.accounts` как список `{code, name}`.

### 3.6 truth.json [v2]

```json
{
  "clean": false,
  "issues": [
    {
      "issue_id": "G21S27",
      "type": "duplicate_invoice",
      "affected_ids": ["invoice/1TNM24", "invoice/F7SF66"],
      "expected_amount_minor": 325000,
      "currency": "EUR",
      "evidence_sets": [["invoice/1TNM24", "invoice/F7SF66", "ledger/CKBBZ4", "ledger/KBYZZ8"]]
    }
  ]
}
```

- `type` принимает одно из значений `duplicate_invoice`, `payment_allocation`, `fx_rate`, `period_cutoff`.
- `affected_ids` это отсортированное каноническое множество. Для дубля это оба счёта. Для разнесения это платёж и счёт. Для курса и периода это `row_id` несущей строки: 1210 у счёта клиенту, 3310 у счёта поставщика, 1030 у платежа.
- `expected_amount_minor` всегда положительное и считается по формуле своего типа из финальных открытых файлов. Порядок инъекций на сумму не влияет.
- `currency`: у дубля и разнесения валюта документа, у курса и периода базовая валюта.
- `evidence_sets` это список допустимых наборов доказательств. Каждый набор достаточен, то есть сумма пересчитывается только из него и `policy.json` (INV-17). Состав набора по типам:
  - `duplicate_invoice`: оба счёта и несущая строка 3310 каждого;
  - `payment_allocation`: платёж, счёт, все строки погашения этого платежа по этому счёту (1210 или 3310 с его `payment_id` и `invoice_id`) и строка 3510 этого платежа;
  - `fx_rate`: документ, несущая строка и `fx/<fx_id>` строки курса за дату по правилу;
  - `period_cutoff`: документ и несущая строка.
- Чистая компания: `"clean": true`, `"issues": []`.
- Дополнительные поля A. `scenario_id` нужен только для отчётов, matcher его не читает. `tolerance_minor` matcher читает. Он равен 1 минимальной единице на каждую конвертацию в формуле, по умолчанию 1, и `expected_amount_minor > 2·tolerance_minor` (INV-20) [кейс §05: задаёт ли кейс допуск сам].
- `je/…` не встречается ни в `affected_ids`, ни в `evidence_sets`.

`truth.json` содержит также `episode_id`. `provenance.json` описан в `docs/DOMAIN_SPEC_A.md` и `docs/tasks/A_generator.md`. Оценщик его не читает.

## 4. Контракт среды

### 4.1 Что уже решено [v2, план]

- `reset(seed, config)` принимает config явно. `step(action)` возвращает пять полей, как в Gymnasium: observation, reward, terminated, truncated, info.
- Действий пять. Страница содержит не больше 50 строк, курсоры стабильны. Лимит 100 шагов. Режимы train и eval.
- Награда равна 0 до submit. Truth читается только при submit. В eval награда и диагностика уходят только в журнал оценщика, `obs`, `reward` и `info` побайтно одинаковы при правильном и неправильном ответе (E-25).
- Политика работает в отдельном процессе и общается со средой JSON-сообщениями через stdin и stdout.

### 4.2 Действия, наблюдения, завершение [кейс §04, код `auditenv/env.py`]

`AuditEnv(mode)` с режимами `train` и `eval`. `reset(seed, config)` возвращает `(observation, info)`, `step(action)` возвращает `(observation, reward, terminated, truncated, info)`. Всё JSON-совместимо.

Действие это JSON-объект `{"action": <имя>, ...аргументы}`:

| Действие | Аргументы | Результат в `observation.result` |
|---|---|---|
| `list_records` | `table` из `ledger`, `invoices`, `payments`, `fx`; `cursor` (`null` для начала); `limit` от 1 до 50, по умолчанию 50 | `{table, records, next_cursor}`, `next_cursor` равен `null` на последней странице |
| `get_record` | `table`, `id` (с префиксом таблицы или без) | `{table, record}` |
| `get_document` | `doc_id` счёта или платежа | `{table, document}` |
| `calculator` | `expression`: только числа, `+ - * /`, скобки, до 200 символов | `{value}` десятичной строкой |
| `submit` | `findings`: объект `findings.json` из §5.1 | `{status: "submitted"}` |

- **Первое наблюдение:** `task`, `manifest`, `policy`, число записей по таблицам, сигнатуры действий, `steps_left` = 100.
- **Наблюдение шага:** только `result` или `error` и `steps_left`.
- **Ошибка:** короткий код без эха ввода: `bad_action`, `unknown_action`, `unknown_table`, `bad_arguments`, `bad_limit`, `bad_cursor`, `not_found`, коды калькулятора. `not_found` одинаков для любого отсутствующего ID.
- **Учёт шагов:** каждый вызов `step` тратит шаг, включая ошибки и submit, всего 100. `inspection_steps` = шаги до submit.
- **Строка от политики, которая не декодируется** (`decode_message`), считается неверным действием `bad_action`: шаг расходуется, эпизод продолжается (решение PM).
- **Завершение:**
  - `submit` даёт `terminated` true.
  - Сотый шаг без submit даёт `truncated` true, пустой ответ и штраф за 100 шагов.
  - Лимит 60 секунд на эпизод даёт то же самое через `truncate()`.
  - После конца эпизода `step` отвечает `episode_over`, шаг не тратится, журнал не меняется.
  - `step` до `reset` отвечает `reset_required`.
- **Награда:**
  - До конца эпизода 0.
  - В `train` терминальная награда возвращается политике, а в `info.grading` лежат `tp, fp, fn, precision, recall, f1` и код ошибки структуры.
  - В `eval` политика всегда видит награду 0 и пустой `info`, наблюдение submit одинаково для любого ответа.
  - Настоящая оценка в обоих режимах пишется в `grader_log`.
- **Курсоры:** стабильные строки `c1.<episode_id>.<table>.<offset>`. Курсор другого эпизода или таблицы даёт `bad_cursor`.
- **config:** готовый эпизод через `episode_dir` или config генератора, см. §4.4.
- **Эпизод:** `auditenv/episode.py` читает раскладку §03. Деньги идут целыми, пустые ячейки CSV становятся `null`, `private/truth.json` читается только при оценке. Документ можно назвать `doc_id`, `invoice_id` или `payment_id` (`Episode.aliases`).

### 4.3 Поведение на краях [v2 и QA, тесты E-03…E-14]

| Ситуация | Поведение |
|---|---|
| битый JSON, неизвестное действие, не тот тип, отрицательный курсор, страница больше 50, строка больше лимита | короткая ошибка в наблюдении, среда живёт дальше, шаг засчитан |
| `get_record` на несуществующий ID, на ID из private, на `je/…`, на путь или SQL | один и тот же ответ «не найдено» по тексту и длине |
| калькулятор | разбор AST, только числа и арифметика, ограничены размер выражения и степени, без имён, вызовов и атрибутов |
| второй submit | отказ, награда и журнал не меняются |
| 100 шагов без submit | `truncated` на сотом шаге, пустой ответ со штрафом за все 100 шагов, дальше ошибка |
| step до reset или после конца эпизода | понятная ошибка без падения |
| курсор из прошлого эпизода | отказ |
| **[предложение B, R-07 и R-09]** сообщение политики больше 1 МБ, NaN, Infinity или `1e999`, целое длиннее 30 цифр, вложенность глубже 32, битый UTF-8, одиночные суррогаты `\ud800…\udfff` в строках и ключах, вход не `str` или `bytes` (подклассы тоже) | короткая ошибка в наблюдении, процесс не падает. Разбор только через `auditenv.server.decode_message`: размер проверяется до `json.loads`, наружу выходит только `BadMessage`. Всё, что декодер принял, записывается в UTF-8 без ошибок. Эти случаи входят в E-03 |

### 4.4 config v1 [docs/tasks/A_generator.md, код `auditenv/config.py`]

`reset(seed, config)` принимает config явно (кейс §04). Есть две формы:

- `{"episode_dir": path}` загружает готовый эпизод (train и dev эпизоды, фикстуры). Других ключей рядом с ним быть не может.
- Любой другой config считается config генератора. Среда нормализует его через `normalize_config` и вызывает `auditenv.generate.generate_episode(seed, config, out_dir)` (роль A) во временную папку с правами 0700. Затем грузит эпизод, держит его и truth в памяти и удаляет папку. Seed должен быть целым числом не меньше 0. Без модуля генератора `reset` даёт `RuntimeError`.

| Ключ | По умолчанию | Допустимо |
|---|---|---|
| `period` | `null` (месяц 2026 года выбирает seed) | `null` или `"2026-MM"` |
| `base_currency` | `"KZT"` | только `"KZT"` |
| `documents` | `[150, 200]` | `[min, max]`, 20 ≤ min ≤ max ≤ 200 (кейс §03, решение PM 150–200) |
| `foreign_pct` | `[0, 60]` | `[min, max]` от 0 до 100 |
| `company_offsets` | `["+03:00", "+04:00", "+05:00", "+06:00"]` | непустой список разных сдвигов `±HH:MM`, порядок не важен |
| `errors` | по 1 каждого из четырёх типов | объект `тип → число ≥ 0`. Типы, которые не названы в переданном объекте, равны 0 |
| `scenarios` | `{"C1": 0, "C2": 0}` | объект `сценарий → число ≥ 0` |
| `twins` | `[3, 8]` | `[min, max]`, 0 ≤ min ≤ max ≤ 20 |

- Всего ошибок не больше 12, C1 считается за 3, C2 за 1 (`total_errors`). Чистая компания: все `errors` и `scenarios` равны 0.
- `fx_rate` и C1 требуют `foreign_pct` max больше 0.
- Неизвестный ключ, неизвестный тип или сценарий, недопустимое значение или `bool` вместо числа дают `ValueError` с коротким текстом, а не тихий дефолт (E-23).
- Результат нормализации содержит все ключи, а списки без смысла порядка в нём отсортированы. Поэтому порядок ключей и элементов не меняет эпизод (E-16). `config_sha256` даёт хеш для `provenance.json` и версий в `configs/`.
- Seed задаёт только случайные значения внутри config. Условия для каждой запрошенной ошибки генератор создаёт сам или даёт `ValueError` (A_generator.md).

### 4.5 Раннер, траектории и изоляция [код `auditenv/runner.py`, `auditenv/run.py`]

- **Связь с политикой.** Политика работает в отдельном процессе и общается JSON-строками через stdin и stdout. Раннер отправляет `{observation, info}` после reset и `{observation, reward, terminated, truncated, info}` после каждого шага. Политика отвечает одной строкой-действием. Каждая строка проходит `decode_message`.
- **Лимиты.** 60 секунд на эпизод. Если политика молчит или закрыла вывод, эпизод заканчивается через `truncate()`. Раннер не падает ни от чего, что делает политика.
- **Песочница (R-03).** В Docker-образе раннер работает от root и запускает каждую политику от пользователя `auditpolicy`. Она:
  - не читает `private/`, журнал оценщика и траектории;
  - не пишет в `/app`;
  - не может послать сигнал раннеру.
  После эпизода все процессы этого пользователя убиваются. Без root (машина разработчика) политика работает от того же пользователя, и `--sandbox required` в этом случае отказывается запускаться. Тесты песочницы `tests/test_sandbox.py` идут от root в Docker-шаге CI.
- **Oracle** работает внутри процесса оценщика (кейс §06) и берёт truth из среды.
- **Траектории** (кейс §09): строки JSON с ключами `episode_id, step, action, observation, reward, terminated, truncated`. Шаг 0 это reset. Нераспознанная строка записывается как `{"bad_message": код}`, действие больше 64 КБ как размер и sha256. U+2028, U+2029 и U+0085 экранируются. Траектории oracle содержат правильный ответ в действиях, поэтому для закрытых эпизодов их не публикуем.
- **CLI:** `python -m auditenv.run --policy {random,reconcile,flag_all,oracle} (--episode-dir DIR | --config JSON) [--seed N] [--policy-seed N] [--mode eval] [--sandbox auto|required|off] [--trajectories PATH] [--grader-log PATH]`. Демо: `make demo`.
- **Seed и config не видны политике (QA N-1, кейс §03).** Командную строку любого процесса читает любой пользователь (`/proc/<pid>/cmdline`), а окружение только его владелец. Поэтому команды, которые запускают политики (`auditenv.run`, `scripts/metrics.py`), сначала вызывают `auditenv.private_args.hide_private_args`. Он один раз перезапускает процесс через `execve` и переносит `--seed` и `--config` в окружение. Пока работает политика, ни одна командная строка их не содержит. Сокращения флагов отключены (`allow_abbrev=False`). Тест `tests/test_private_args.py` ищет seed во всех `/proc/*/cmdline` из процесса политики. Новая команда, которая запускает политики, обязана делать так же.

## 5. Оценка

### 5.1 Вывод агента [кейс §05, решения PM 20.11]

`submit` принимает `findings.json`: `{episode_id, findings: [{type, affected_ids, claimed_amount_minor, currency, evidence_ids, explanation}]}`. Имена полей заданы константами `F_*` в `auditenv/grader/matcher.py` и `auditenv/submission.py`.

**Неверная структура даёт −1 и завершает эпизод** (кейс §05). Среда проверяет весь `findings.json` до оценщика, функция `auditenv.submission.check_submission`. Код ошибки уходит в журнал оценщика.

| Поле | Допустимо |
|---|---|
| `episode_id` | строка, равна `episode_id` текущего эпизода |
| `findings` | список не длиннее 30 |
| `type` | одно из четырёх имён типов |
| `affected_ids` | непустой список строк |
| `claimed_amount_minor` | `int`, не меньше 0. `bool`, `float` и строка не принимаются |
| `currency` | три латинские буквы в верхнем регистре |
| `evidence_ids` | список строк длиной не больше 10, повторы тоже считаются в длину |
| `explanation` | строка не длиннее 1000 символов. На награду не влияет |
| лишние ключи | игнорируются, и наверху, и внутри вывода |

Оценщик остаётся вторым слоем. Он сам проверяет каждый вывод по тем же правилам, вывод с другим форматом засчитывает как FP (`invalid_findings`) и никогда не бросает исключение. Принимаются только типы, которые даёт `json.loads`: ровно `dict`, `list`, `str` и `int`, проверка идёт по точному типу. Сам список выводов должен быть ровно `list`, иначе `TypeError`.

### 5.2 Правило совпадения [v2 и R-01: строгое, если §05 допускает]

Вывод совпадает с ошибкой из truth, только если выполнены все пять условий:

1. `type` равен.
2. Множество `affected_ids` равно множеству из truth после снятия известных префиксов.
3. `|claimed_amount_minor − expected_amount_minor| ≤ tolerance_minor`.
4. `currency` равна.
5. `evidence_ids` является надмножеством хотя бы одного набора из `evidence_sets`, и `len(evidence_ids) ≤ 10`.

Если сверять только тип и ID, сумма, валюта и доказательства перестают влиять на награду. Если засчитывать пересечение ID, распыление ID получает +0.333 без расследования (QA v0.1, раздел «Награда и matcher»).

Детали сравнения **[предложение B, реализовано]**:

- Документ можно назвать и `doc_id`, и `invoice_id` или `payment_id` (кейс §03, решение v2). Среда передаёт оценщику словарь `aliases` из `doc_id` в канонический ID записи, он применяется после `normalize_id` и к выводу, и к truth.
- ID сравниваются после `normalize_id`. Известный префикс снимается один раз: `allocation`, `counterparty`, `doc`, `fx`, `invoice`, `ledger`, `line`, `payment`. Всё остальное, включая `je/…` и регистр, сравнивается как есть. Поэтому `fx/2026-09-14/USD/KZT` и `2026-09-14/USD/KZT` совпадают. Префикс другой таблицы при верном ID не мешает: ID уникальны между таблицами.
- `tolerance_minor` берётся из issue, по умолчанию 1. Граница включается: при допуске 1 разница в 1 засчитывается, в 2 уже нет.
- truth проверяется при загрузке. `clean` должен быть равен «issues пуст», `issue_id` уникальны, `type` это строка из четырёх имён, `expected_amount_minor` положительный `int` больше двух допусков (INV-20), каждый набор доказательств содержит от 1 до 10 ID, `je/…` не встречается. Нарушение даёт `ValueError`: это баг генератора, а не ответа агента.

### 5.3 Сопоставление [v2]

Сопоставление строит максимальное паросочетание по допустимым парам «вывод и ошибка». Одна ошибка закрывается не больше чем одним выводом, повтор вывода идёт в FP. В C1 у периода и курса одинаковые `affected_ids`, поэтому тип обязан участвовать в паре.

Ничья разрешается детерминированно **[уточнено B]**. Из всех максимальных паросочетаний выбирается лексикографически наименьшее. Ошибки идут по возрастанию `issue_id`, и каждая получает вывод с наименьшим номером, при котором паросочетание остаётся максимальным. Номера выводов начинаются с 0. На TP, FP, FN и награду выбор не влияет, он фиксирует только пары `matched` в журнале оценщика. Тест сверяет результат с перебором на 300 случайных графах.

### 5.4 Награда [v2, формула организаторов без изменений]

```
P = TP / (TP + FP),  R = TP / (TP + FN),  F1 = 2PR / (P + R)
F1 = 1, если пусты и truth, и вывод;  F1 = 0, если TP = 0 в остальных случаях
reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)
```

- Арифметика точная, в `Fraction`, перевод во `float` делается один раз в конце. 40 шагов дают ровно 0.92.
- Precision и Recall считаются по кейсу §05: при нулевом знаменателе они равны 0. F1 при пустых эталоне и выводах равен 1. На награду P и R не влияют, она считается через F1 по счётчикам.
- API: `auditenv.grader.score(findings, truth, inspection_steps)` возвращает `tp, fp, fn, precision, recall, f1, reward, matched, invalid_findings`. `timeout_score(truth)` возвращает пустой ответ со штрафом за 100 шагов. Результат пишется только в журнал оценщика.
- `inspection_steps` равен числу шагов расследования, submit в него не входит [кейс §05: считаются ли калькулятор и неверные действия].
- Тайм-аут и лимит шагов дают пустой ответ и штраф за все 100 шагов. На чистой компании это +0.8, ниже молчания. Это записываем в DESIGN.md (R-02).
- **[предложение, R-07]** Лимит submit задаём в правилах ввода, например не больше 100 выводов и 1 МБ. Сверх лимита отказ, формулу не трогаем. Лимит 1 МБ уже действует на любое сообщение политики, а не только на submit: см. `decode_message` и §4.3. Лимит числа выводов ждёт среды.
- Matcher B обязан повторить колонку STRICT на всех 23 случаях `qa_reward.py` (E-24).

## 6. Инварианты

Полный список INV-01…INV-24 лежит в спецификации A. INV-01…INV-16 проверяет генератор A. INV-17…INV-24 проверяет независимый верификатор B и стресс-тест на 300 seed.
