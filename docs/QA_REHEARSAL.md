### Пять главных рисков

1. **README и DESIGN.md (Н-1).** Жюри читает README первым, а там написано «Генератора компаний ещё нет». Записки о дизайне нет, хотя её требует кейс §09. Это блок инженерии и первое впечатление. B правит сегодня.
2. **Изоляция вне Docker (Н-3).** Без root политика работает от того же пользователя. Враждебная проба вне контейнера прочитала `truth.json` и `provenance.json` всех эпизодов в `episodes/` и `runs/`, журнал оценщика, окружение раннера и его открытые файлы. Ещё она смогла писать в репозиторий и послать сигнал раннеру. Если жюри запустит закрытый прогон не в нашем образе, это утечка, а утечка блокирует оценивание (§10). Нужно, чтобы README прямо требовал Docker для закрытого прогона и чтобы `--mode eval` без песочницы хотя бы громко предупреждал.
3. **Чужую политику нечем подключить (Н-4).** `python -m auditenv.run --policy` принимает только четыре имени. Политика организаторов (§06, решение PM §8.5) запускается только через Python API `run_subprocess_episode`, которого в README нет. Это первое, что упрётся в части B, пункт 9.
4. **Config выполняется не полностью и молча (Н-2).** На маленьких книгах `twins: [20, 20]` даёт 6, 7 или 12 двойников без `ValueError`. Жюри обещает «новые сочетания параметров», и крайние значения будут как раз у них.
5. **Порядок reconcile выше random держится на доле чистых.** На 20 эпизодах среднее −0.290 у reconcile против −0.508 у random. Но на чистых книгах reconcile получает −1, а random +0.97, потому что random почти никогда ничего не сдаёт. Порядок переворачивается, когда чистых больше примерно 32%. Кейс этого не требует, но жюри будет сравнивать диагностику.

### Отступления от задания и вопросы

- **Тест песочницы лежит в `tests/`, а не только в `qa/`.** Задание просит оформить пробы песочницы тестами, которые выполняются в Docker-шаге CI. Но Docker-шаг запускает только `unittest discover -s tests`, а `scripts/verify.sh` принадлежит B. Поэтому добавлен один новый файл `tests/test_rehearsal_sandbox.py`: он только вызывает проверки из `qa/rehearsal/probes.py`. Чужие файлы не менялись.
- **«Равенства до внесения ошибки»** (§10, блок данных). Вопрос закрыт заданием `docs/tasks/V_rollback.md`. Книгу до ошибок V восстанавливает по `provenance.json` и проверяет строгим V с пустым эталоном, подробно в разделе «Откат provenance» ниже.
- **Формат provenance в SPEC.md не описан.** §3 отсылает к `docs/DOMAIN_SPEC_A.md` и `docs/tasks/A_generator.md`, а раздел о provenance V не читал. Поля отката взяты из `V_rollback.md` и сверены с данными 60 эпизодов: `injections[].order`, `changes[].record` вида `ledger/ID`, `field`, `before`, `after`. Других видов изменений в данных нет. Ключа `row` в SPEC тоже нет, он придёт по `B_afternoon.md`, пункт 3. Откат принимает `row` с полями ровно как у строки книги. Значения могут быть такими, как их читает `auditenv.episode` (целые в `*_minor`, `null` для пустых), или строками CSV. Предлагаю дописать формат provenance в SPEC §3 одним абзацем.

### Откат provenance (`docs/tasks/V_rollback.md`)

Код в `auditenv/verify/rollback.py`. Откат идёт на копии в два шага.

1. Отмена изменений: ошибки от большего `order` к меньшему, изменения внутри каждой с конца.
   - Запись с `after: "created"` удаляется.
   - Запись с `before: "removed"` возвращается из `row`. Строка книги встаёт на своё место по `je_id`, потому что `ledger.csv` упорядочен по `je_id`.
   - У поля текущее значение должно точно равняться `after`, тогда ставится `before`.
2. Пересчёт и проверка. В `manifest.json` пересчитываются `counts` и `documents`, truth становится `{"clean": true, "issues": []}`. Затем строгий V, с объёмом INV-03.

Любое несовпадение provenance с файлами даёт замечание `ROLLBACK` с номером ошибки и записью. Строгий V тогда не запускается, потому что книга неполна.

Чтобы откат не проходил впустую: на итоговой книге с пустым эталоном V находит по замечанию на каждую ошибку на всех 15 train и dev с ошибками, а после отката ни одного. Тесты в `tests/test_rollback.py` гоняют два эпизода (train 1000 и dev 2004) и следующие случаи provenance:
- `removed` со строкой и без неё;
- `removed`, когда запись осталась;
- `after` не совпадает;
- `created`, когда записи нет;
- неизвестное поле;
- неизвестная таблица;
- повтор `order` и отсутствие файла.
