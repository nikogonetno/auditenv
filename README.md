# auditenv. RL-среда для ИИ-аудитора

Офлайн-среда для обучения и проверки ИИ-аудитора. Генератор создаёт вымышленную компанию за один месяц: счета, платежи, разнесения, курсы и книгу проводок. В книгу вносятся скрытые ошибки четырёх типов: дубль счёта поставщика, ошибка разнесения платежа, неверный курс и ошибка периода. Рядом лежат корректные двойники, похожие на ошибки. Агент расследует книгу узкими инструментами и сдаёт выводы с доказательствами. Оценщик сверяет их с эталоном строгим правилом.

Все данные синтетические.

## Статус

Чекпоинт 1, роль B. Готовы оценщик по кейсу §05, среда `reset/step` с пятью действиями §04, калькулятор, загрузчик эпизода в схеме §03, раннер с политикой в отдельном процессе (JSON через stdin и stdout), четыре базовые политики кейса §06 (случайная, простая сверка, «пометить всё», oracle), запись `trajectories.jsonl`, config v1 (`auditenv/config.py`) и стресс-тест (`make stress`). Генератора компаний ещё нет (роль A): `reset(seed, config)` вызовет его, когда он появится, а пока среда работает на готовых эпизодах, а для тестов есть `tests/fixtures/mini_v03`, golden v0.1 в схеме §03. Текст кейса лежит в [docs/CASE.md](docs/CASE.md), решения PM в [docs/PM_DECISIONS.md](docs/PM_DECISIONS.md), контракт в [SPEC.md](SPEC.md).

## Быстрый старт

Нужен только Python 3.11 или новее, без установки пакетов.

```bash
make verify
```

Демо: четыре базовые политики в режиме eval на тестовом эпизоде, траектории и журнал оценщика пишутся в `runs/`:

```bash
make demo
```

Одна политика на своём эпизоде:

```bash
python3 -m auditenv.run --policy oracle --mode eval --episode-dir tests/fixtures/mini_v03 --trajectories runs/t.jsonl
```

В Docker, без сети:

```bash
make docker-verify
```

## Что проверяет `make verify` сейчас

1. Все модули пакета импортируются, runtime-зависимостей нет.
2. Golden пересобирается побайтно одинаково при `PYTHONHASHSEED` 0, 1 и 12345. Отдельный тест подтверждает, что сид действительно доходит до дочернего процесса.
3. Все 8 сумм эталона пересчитываются только из доказательств.
4. В открытых файлах нет закрытых слов, ID эталона и колонок с подчёркиванием.
5. ID уникальны между таблицами.
6. Детектор QA находит те же 8 ошибок. Шаг падает только на критичной находке.
7. Оценщик: все случаи таблицы QA (E-24), порядок выводов (E-26), ID с префиксом и без (E-27), неверный формат вывода (E-28), максимальное паросочетание, одинаковый результат при разных `PYTHONHASHSEED`, тесты повторной проверки QA (`tests/test_qa_recheck1.py`).
8. Разбор сообщений политики `auditenv.server.decode_message`: размер, NaN и Infinity, длинные целые и глубокая вложенность дают короткую ошибку, а не падение процесса (R-09).

Независимые скрипты QA для оценщика лежат в `qa/`. Их запускают вручную, в `make verify` они не входят, потому что мутационный прогон занимает около минуты:

```bash
python3 -I qa/qa_recheck_grader.py .
```

```bash
python3 -I qa/qa_attack_grader.py .
```

```bash
python3 -I qa/qa_mutate_grader.py .
```

## Известные ограничения

- Генератора компаний (роль A) ещё нет. Среда работает на готовых эпизодах в схеме §03, тестовый эпизод `tests/fixtures/mini_v03` собран из golden v0.1.
- Песочница политики (отдельный пользователь) действует только в Docker-образе, где раннер запущен от root. На машине разработчика политика работает от того же пользователя и могла бы прочитать файлы на диске.
- Без root `make verify` пропускает тесты песочницы `tests/test_sandbox.py`: им нужен пользователь `auditpolicy`. В Docker-образе и в CI они выполняются. Вне Docker пропускается ещё проверка прав `private/` в образе.
- Политика «простая сверка» нарочно наивная. На `mini_v03` она попадается на подписку, ловушку C2, счёт около полуночи по UTC и счёт в субботу с курсом пятницы (TP 7, FP 4, FN 1).
- Риск R-08 (умный спрей по `period_cutoff` на маленькой книге) описан в SPEC §8.
